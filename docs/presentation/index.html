How we built it · The model

Which model we use and how it is configured

Modelqwen3-vl:4b-instruct, 4.4B parameters (V5, V6 on the MacBook: qwen3-vl:8b-instruct, 6.1 GB)
Where it runslaptop, Ollama server at localhost:11434
QuantisationQ4_K_M, 4 bits per weight
Memory for weights4.4B × 0.5 byte + projector ≈ 3.3 GB
Context windownum_ctx 8,192 tokens (Ollama default 4,096 is too small for tree + image)
Samplingtemperature 0, seed 42, top-p left at default
Outputmax 400 tokens, JSON-schema constrained
  • Free after download, slow, small only
  • Temperature 0 + fixed seed, so a result can be repeated
  • The variant that answers at once, not the one that thinks first
  • Every run records name, size, quantisation and digest
Tag 1, Lecture B Part 5: drei Orte, wo ein Modell laufen kann; Speicher = Parameter × Bytes pro Parameter; Quantisierung; "if you change quantisation, re-run". Top-p haben wir nicht angefasst (Ollama-Standard 0.9), bei Temperatur 0 spielt es keine Rolle, weil immer das wahrscheinlichste Token gewählt wird. How we built it · Agent design

Agent design: the eight stages of one step()

0 budgetstep limit checked first
1 observescreen → elements or screenshot
2 decideprompt → one JSON action
3 validateparse, check, retry with the error
4 groundindex → pixel, in code
5 checkpayment ban, app scope, loop guard
6 actexecute on the device
7 feedbackdid the screen change? one history line

C = code we wrote  ·  M = the model

Harness partWhat it decidesWhere in step()
Loop controlwhen to call the model again, when to stopstage 0, stop rules
Context assemblywhat goes into the window, inside the budgetstage 1, prompts.py, memory.py
Tool dispatchturn the JSON into a real tap on the devicestages 4 and 6
Error recoveryparse failed, no effect: retry, repair or give upstages 3 and 7
Guardrailswhat is forbidden, what gets loggedstage 5, guardrails.py
Folie 40 Tag 1: "Together these five are called the harness: everything around the model that you write. None of it is the model." Course reader: nur der Harness geändert, Genauigkeit von 53 % auf 66 %. Kurzform: Das Modell trifft nur die Entscheidung, was als Nächstes getan wird. Alles davor und danach ist unser Code. Zusammen ist das der Agent. Ob die Aufgabe erledigt ist, sagt der Prüfer von AndroidWorld, nicht das Modell. Sprechtext: notes/Sprechtext-Folien.md.

How we built it · How it points

How the agent points: coordinates vs. index

By coordinate V1

{"action_type": "click", "x": 540, "y": 735}

The model produces the numbers. A 20-pixel error is a tap on the gap between two rows, and nothing reports an error.

By index V2V3

{"action_type": "click", "index": 3}

Our code looks element 3 up in the tree. It either finds it or it doesn't: a failure we can see and log.

Zitate Tag 1: "Most GUI-agent failures are pointing failures, not reasoning failures", "Where grounding happens decides who you can blame". Das ist genau die eine Änderung zwischen V1 und V2. Mündlich: V1 prüft die Zahlen des Modells nie, ein falscher Tipp bleibt stumm. V2/V3: der Index muss im Tree existieren, ein falscher Tipp wird vom Code abgefangen, bevor er passiert. How we built it · What the model sees each step

Old screens are never resent: one line per step, status last

system   role · action space · rules      (stable prefix, cached)
user     GOAL: Create a new contact for Hugo Pereira …
         HISTORY:
         1. navigate_home -> executed
         2. click [6] "Search" -> BLOCKED: home screen
         3. open_app contacts -> executed
         CURRENT SCREEN: [0] … [13]        (this step only)
         STATUS: step 4 of 12 · app: contacts
         note: number +13920741751      (most volatile, last)
  • A tool-call loop, but compressedeach step gets a fresh prompt: the old screen is dropped, one text line per step stays. 20 kept screenshots would cost 20,000+ tokens
  • Stable prefix first, volatile last, so the KV cache hitsthe model reuses what it computed for an unchanged beginning: fixed rules first, the ever-changing status line last
  • History and status are written by code, not by the model"BLOCKED" or "changed nothing" is recorded by our code, so it is a fact. In V3 the note line carries a value into the next app
Tag 2 Folie 11 (Multi-Turn mit Tool Calls): Modell entscheidet, Framework führt aus, Ergebnis kommt als Nachricht zurück. Bei uns dasselbe, nur komprimiert: statt den Verlauf anzuhängen, bauen wir den Prompt jeden Schritt neu. Tag 2 Teil 2 (KV-Cache): nur ein unveränderter Prefix kann wiederverwendet werden, deshalb System-Prompt und Action Space vorn und fest, Status Bar ganz hinten. Ehrlich dazu: weil die User-Nachricht jeden Schritt neu ist, trifft der Cache nur den System-Prefix. Anhängen würde mehr cachen, aber das Fenster wächst mit jedem Screenshot. Wir haben uns für flache Kosten entschieden.

How we built it · Guardrails

Guardrails: in the code, before the action, no off switch

  • Step limit
  • Payment ban, layer 1: app scope
  • Payment ban, layer 2: deny rules
  • Loop guard V3

A guardrail firing in our run V2

2. click [6] "Search"
   -> BLOCKED: do not tap or type on the home screen.
      Open the app you need with open_app and its exact name.
3. open_app contacts -> executed

Step 2: the model wanted to tap the home-screen search. The code refused, and told the model why. Step 3 did it right.

Pflicht-Minimum des Dozenten (Tag 1): Schrittlimit + Zahlungsverbot, im Code, vor der Aktion. Tag 4: "Layered constraint design": Prompt-Regel kann ignoriert werden, Enforcement Layer nicht. Mündlich: Schrittlimit = harte Obergrenze, Task-Budget darf nur senken; Zahlungsverbot Schicht 1 = App-Scope (nur in der erlaubten Liste offline-Apps handeln, sonst nur back/home/wait/open_app); Schicht 2 = Deny-Regeln (nichts auf Pay/Buy/Subscribe, keine Karten- oder IBAN-Felder, keine gültige Kartennummer tippen); Loop Guard V3 = gleiche Aktion auf unverändertem Bildschirm zweimal erlaubt, beim dritten Mal blockiert. Vorher stand rechts der Test: ein Skript-Modell füllt ein Bezahlformular aus und tippt "Pay", 0 Aktionen erreichen das Gerät (tests/test_guardrails.py, 209 Tests grün); jetzt nur mündlich als Beleg, wenn gefragt. How we measured · When a run stops, and what counts

A run ends for one of five reasons. Only one of them can be a PASS.

Stop reasonWho decidedCan be PASS?
model_donemodel says status: completeyes, if the verifier agrees
model_infeasiblemodel gives upno
step_limitcode: budget reachedno, even if the screen is right
loop_abortcode: same action, same screen, 3× blocked (V3)no
erroremulator or model server brokeERROR, excluded from rates

PASS means both:

  • the agent itself reported complete
  • AndroidWorld's checker returns 1.0 on the device state

Running out of steps is never counted as done, and a correct screen without the report is still a FAIL: the agent has to know it is done.

Tag 1 "Three ways the loop breaks": endet nicht (→ Schrittlimit), falscher Tool-Aufruf (→ Validierung), sagt fertig und ist es nicht (→ Verifier). Der Verifier ist AndroidWorlds eigener Check (task.is_successful), nicht unser Code. Sprechtext: notes/Sprechtext-Folien.md.

What happened · Was it reliable?

Reliability check: strong on constraints, weak on verification. V3 added it, and it misfired.

Reliability leverWhat it asksV1 / V2V3
Goal clarityWhat counts as success?✓ the task text, plus AndroidWorld's checker on the device state✓ same
Observable stateWhat can the agent see?✓ the current screen every step; history lines show what changed✓ same
FeedbackDoes it know what happened?weak: "executed""your action changed nothing": wrong on Save, Markor autosaves without a visible change
VerificationDid the result work?none before done: the missing surname goes throughcheck step with the same 4B model: accepted the missing surname 3 of 3 times
RecoveryRetry, revise, roll back or stop?invalid JSON: retry with the error, 2×. Timeout 300 s: ERROR+ loop guard: same action, same screen, 3× blocked. Fired on Save, ended 3 runs
ConstraintsWhich rules must the system enforce?✓ in code, not in the prompt: step limit, payment ban, app scope✓ same, held in all 81 runs on two machines

Every V3 mechanism assumes that a successful action changes the screen. Where that assumption fails, the safety net turns a pass into a fail.

Stand 08.10. nach allen 27 Läufen: V3 0/9. Tag 4 Folie "Core Concepts" (goal clarity, observable state, actionability, feedback, verification, recovery) und "Four Reliability Levers" (feedback, recovery, verification, constraints). Ehrliche Einordnung: V1/V2 haben Constraints und Beobachtbarkeit, aber keine Verifikation vor done. Das erklärt false_done bzw. lost_value. V3 hat Feedback, Verifikation und Loop-Guard ergänzt; alle drei beruhen auf der Annahme "erfolgreiche Aktion = sichtbare Änderung". Markor speichert automatisch ohne sichtbare Änderung, also feuern alle drei auf Save falsch (Save-Schleife, loop_abort, Prüfschritt lehnt korrekte Notiz ab). Der Prüfschritt vor done nutzt dasselbe 4B-Modell und hat den fehlenden Nachnamen 3 von 3 Mal durchgewinkt. Sprechtext: notes/Sprechtext-Folien.md.

The lecture's four places for a fix: Knowledge · Instructions · Programs · Parameters. "A rule that must never be bypassed → Programs." A judgement you can state in one sentence → Instructions.

Tabelle "How to choose" / "Put the fix in" aus Tag 5 (Knowledge, Instructions, Programs, Parameters). Stand nach allen Läufen: Programs hat funktioniert, wo es um Mechanik ging (Zeigen, App-Wahl), nicht, wo es um Urteil ging (ist der Kontakt vollständig? ist gespeichert?). Für Urteil braucht es entweder ein stärkeres Modell (Parameters) oder Code, der den echten Zustand liest statt den Bildschirm (Kontaktdatenbank, Dateiliste). Markor-Autosave ist App-Wissen in einem Satz, gehört in eine Skill-Datei (Instructions), nicht in einen generischen Loop-Guard. Q&A: warum nicht einfach den Prompt ändern? What we changed and learned · Key findings

Four things the runs told us that a demo would not have

  • Where grounding happens matters more than prompt wordingmoving it into code made every step 3× faster and removed the taps into nothing. It also exposed the next weakness: lost values
  • Every safety mechanism encodes an assumption about the appV3's hint, loop guard and check step all assume a visible change. Markor autosaves. 2 of 9 became 0 of 9
  • A verifier as weak as the actor adds cost, not safetythe check step was the same 4B model; it accepted the missing surname every time
  • Three runs per task find patterns, not rankingsone run moves a task by 33 points; the trajectories carry the findings, not the rates

What we changed and learned · Outlook

What we would do next, in this order

  • Verify from the device, not from the screenread the contacts database and Markor's file list over adb before "done": catches lost_value and false_done with any model (Programs)

Backup · Technical · Payment ban

Payment ban: two layers, six deny rules, no off switch

Layer 1 · app scope

  • open_app only by exact name from the allow-list (Contacts, Markor, Simple SMS Messenger, …)
  • Any action while a package outside the scope is in front is blocked, except leaving it
  • Home-screen taps are blocked: apps are opened by name, never by searching the launcher

Layer 2 · deny rules, checked before every action

aopening an app that exists to buy or pay
banything but leaving while such an app is visible
canything but leaving on a payment form (a payment field on screen, or two payment signals)
dtaps and typing on, or next to, an element labelled pay / buy / checkout / add to cart: every element under the tap point is hit-tested, and the row around the label too
etyping or Enter without a known target while a payment element is on screen
ftyping a card number (13 to 19 digits, Luhn check) or an IBAN (mod-97 check), in one go or in consecutive chunks

A blocked action costs a step and tells the model why: "BLOCKED by the payment guardrail: … Go back and continue without paying."

gui_agent/guardrails.py, Tests in tests/test_guardrails.py (ein gescriptetes Modell, das "Pay" tippt, erzeugt null Geräteaktionen).
